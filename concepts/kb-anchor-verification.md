## 1. 문제의식 — 라벨러의 자기 편향

자동 라벨러의 출력만 보고 품질을 판단하는 것은 **자기 심판**이다:
- 단일 LLM/모델의 출력은 해당 모델의 pretrain 편향·프롬프트 편향을 그대로 반영
- 두 모델 간 합의(`concepts/inter-annotator-agreement.md`)도 **두 모델이 같은 편향을 공유**하면 부당하게 높게 나올 수 있음
- Gold 수작업 평가는 비용 장벽이 큼

해결: **라벨러와 데이터 출처가 완전히 다른** 외부 KB 에서 타입을 독립 유도하고, 이를 "닻(anchor)"으로 삼아 라벨 품질을 감사(audit)한다. Wikipedia 편집자·Wikidata 커뮤니티는 라벨러 모델의 훈련과 무관하게 타입 정보를 구조화한다.

## 2. 앵커 검증의 기본 파이프라인

```
엔티티 표면형 (예: "Hà Nội")
  └─ [1] 표면형 → KB 식별자 (언어별 위키 페이지 → Q-ID)
       └─ [2] 식별자 → 구조화된 타입 정보 (P31 claims)
            └─ [3] KB 타입 → 관심 스키마 타입 (매핑 테이블)
                 └─ [4] 시스템 라벨과 비교 → 일치율 집계
```

**중요한 설계 원칙**: 앵커 검증은 **감사(audit) 용도**이며 라벨을 **고치지 않는다**. 불일치 케이스를 샘플링해 리뷰·리포트를 만들 뿐이다. 자동 정정은 또 다른 편향 고리를 만들 수 있으므로 별도 의사결정 단계로 분리한다.

## 3. Wikipedia + Wikidata 를 쓰는 이유

### 3.1 Wikipedia 인터링크의 역할

다국어 처리의 핵심 난점은 "다른 언어판에서 같은 엔티티를 어떻게 식별하느냐"다. Wikipedia 는 각 언어판 간 링크를 Wikidata 에 중앙집중화해, **임의 언어의 표면형 → 언어 독립 식별자 (Q-ID)** 변환이 API 한 번이면 가능하다.

### 3.2 Wikidata 의 구조화 데이터

Wikipedia 본문은 자연어라 기계 추론이 어렵지만, Wikidata 는 동일 엔티티에 **Property-value claim 트리플**을 사람이 유지한다. 여기서 타입 정보의 핵심이 P31(instance of)과 P279(subclass of)다.

### 3.3 규모와 커버리지

- Wikidata 엔티티 수: 1억+ (2025 시점)
- 주요 언어의 Wikipedia 커버리지: 50–70%의 대중적 엔티티
- 소수 언어: 30% 미만이 일반적

즉 **앵커 검증이 닿는 범위는 데이터의 부분집합**이며, 이를 통해 얻은 일치율은 전체 품질 지표가 아니라 "매핑 가능한 부분집합의 신뢰도"로 읽어야 한다.

## 4. P31 / P279 — 타입 유도의 두 축

| 속성 | 역할 | 예 |
|---|---|---|
| **P31 (instance of)** | 이 엔티티가 속한 "종류" | `Q1858` (Hanoi) → P31 → `Q515` (city), `Q5119` (capital city) |
| **P279 (subclass of)** | 한 종류가 상위 종류의 하위 클래스임을 선언 | `Q5119` (capital city) → P279 → `Q515` (city) |

### 4.1 P31 만으로 충분한가

P31 만 쓰면 매핑 테이블이 수만 엔트리로 폭발한다. 예: `city`, `capital city`, `big city`, `municipality`, `town`, `village`, `human settlement` 모두 독립적으로 매핑해야 "모두 `LOC`" 규칙이 성립.

**P31 + P279 를 함께 타고 올라가면** 하위 클래스는 상위 매핑을 상속하므로 매핑 테이블이 작아진다. 단, 그래프 탐색 깊이와 루프 방지를 설계해야 한다.

### 4.2 현업 사례: NECKAr

Geiß & Gertz (2017) 의 NECKAr 는 Wikidata 전체를 P31/P279 그래프로 분류해 **800만+ 엔티티**를 PER/LOC/ORG 3종으로 범주화했다. 앵커 검증 용 매핑 테이블의 사실상 참조 구현.

### 4.3 복수 P31 의 처리

한 엔티티가 여러 P31 을 가지면 해석이 갈린다. 전략:
- **첫 매칭(Lexicographic)** — 테이블 스캔 중 처음 매핑되는 타입 채택. 구현은 간단하나 테이블 순서에 의존.
- **우선순위 태그** — 매핑 테이블에 타입별 우선순위를 부여.
- **다수결** — 여러 P31 에서 얻은 타입을 투표해 가장 흔한 것 채택. 역사적 정치체(`city` ∩ `former country`) 같은 본질적 모호 케이스에서 안정적.

## 5. 매핑 테이블 설계

KB 의 수만 개 P31 Q-ID 를 관심 스키마(10종 내외)로 축소하는 작업은 **수작업 큐레이션**이 핵심이다. 설계 지침:

1. **빈도 우선** — 라벨링한 엔티티에서 상위 빈도 unmapped Q-ID 를 먼저 추가. Long tail 은 diminishing return.
2. **메타/비엔티티는 의도적 미매핑** — `disambiguation page`, `taxon`, `Wikimedia category` 등은 매핑하면 노이즈가 더 커진다.
3. **경계 케이스 문서화** — "holding company"를 `ORG`로 매핑할 때 자회사 케이스에서 어떻게 작동하는지 주석.
4. **확장 영향 추적** — 매핑 테이블을 확장하면 (a) mapped 엔티티 수 증가 (b) 일치율이 개선 또는 악화 방향으로 움직인다. 확장 전/후 비교를 기록해 어떤 엔트리가 "좋은 확장"이었는지 판단.

## 6. 집계 지표

표준 리포트 포맷:

| 지표 | 정의 |
|---|---|
| Total entities | 검증 대상 엔티티 수 (라벨러 출력) |
| With KB identifier | 표면형에서 식별자 확보 가능한 비율 |
| With type claims | 식별자에 P31 claim 이 있는 비율 |
| Mapped to schema | 매핑 테이블로 스키마 타입 유도 가능한 비율 |
| Agreement | Mapped 중 시스템 라벨과 앵커 타입이 일치한 비율 |
| Per-type agreement | 각 스키마 타입별 일치율 (어느 타입이 약한지 드러냄) |
| Top unmapped | 자주 등장했지만 매핑되지 않은 P31 Q-ID (테이블 확장 후보) |
| Mismatch samples | 불일치 케이스 샘플 (수작업 원인 분석용) |

### 6.1 불일치의 3가지 카테고리

수작업으로 불일치 케이스를 훑을 때 원인을 분류:

- **카테고리 A — 라벨러 오류, 앵커 정정**: 앵커 타입이 옳고 라벨러가 틀렸음. 라벨러 품질 지표.
- **카테고리 B — 앵커 오류, 라벨러 정정**: 라벨러가 옳고 앵커 쪽이 매핑 누락·과도한 P31 일반화. 매핑 테이블 개선 후보.
- **카테고리 C — 진짜 모호**: 양쪽 모두 타당. 스키마 정의 재검토 또는 다중 타입 허용 여부 결정.

## 7. 한계와 체계적 오류

1. **커버리지 공백** — Wikipedia 미등재 엔티티(개별 인물·세부 지명·제품 인스턴스)는 검증 대상에서 아예 빠진다. 소수 언어일수록 심함.
2. **리다이렉트 왜곡** — 표면형이 다른 개념으로 리다이렉트되면 엉뚱한 Q-ID 가 할당된다 (예: 곡명 → 가수 페이지).
3. **매핑 테이블 편향** — 사람 큐레이션이라 누락된 하위 클래스가 체계적 오류를 만든다 (예: `national library` 미매핑 → `publisher` 로 잘못 추론).
4. **P31 복수값의 순서 의존성** — 첫 매칭 전략은 테이블 순서에 의존. 결정론적이지만 edge 케이스에서 잘못된 우선순위를 만들 수 있음.
5. **독립성의 상대성** — Wikidata 자체가 Wikipedia 편집자에 의존하므로 "완전히 독립된 증거"는 아니다. 다만 타겟 라벨러(LLM·BERT·규칙)와는 데이터 출처가 다르다.

## 8. 다른 검증 방법과의 비교

| 방법 | 증거 출처 | 장점 | 약점 |
|---|---|---|---|
| Gold 수작업 평가 | 사람 전문가 | 절대 기준 | 비용 높음 |
| Cross-model 합의 (`concepts/inter-annotator-agreement.md`) | 서로 다른 LLM/모델 | 규모 확장 용이 | 편향 공유 위험 |
| **KB 앵커** | 외부 구조화 KB | 라벨러와 데이터 출처 분리 | 커버리지 제한, 매핑 큐레이션 비용 |
| Self-consistency | 같은 모델의 다수 샘플링 | 저비용 | 모델 편향 그대로 |

실무에서는 **여러 방법을 조합**한다. 예: Cross-model κ 로 일관성 확인 + KB 앵커로 편향 감사 + 소규모 gold 샘플로 절대 기준 고정.

> **생성 시점 검증과의 관계**: 위 표는 *이미 라벨된* 데이터를 사후 감사하는 방법이다. 합성 데이터를 **만드는 루프 안에서** verifier-judge 가 풀이를 채점하는 방식(`concepts/agentic-data-generation.md`)은 검증 시점이 다르지만, "생성자와 분리된 독립 심판으로 자기 편향을 피한다"는 원리는 동일하다. 자동 심판이 생성자와 같은 모델 편향을 공유하면 부당히 후해질 위험도 같다.
