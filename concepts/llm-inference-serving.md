# LLM 추론 서빙

> prefill과 decode의 실행 시간을 나눠 측정하고, 모델·배치·캐시·하드웨어 조건에 맞는 최적화를 선택한다.

## 개요

학습한 모델로 답을 생성하는 과정이 **추론(inference)**이며, 여러 요청을 지속적으로 처리하도록 제공하는 것이 **서빙(serving)**이다. 같은 모델도 입력·출력 길이, 요청 부하, 캐시 적중률에 따라 성능이 달라진다.

## 핵심 원칙

- **토큰 수와 실행 시간을 구분한다.** prefill은 입력 토큰을 병렬 처리하고 decode는 출력 토큰을 순차 생성하므로, 입력·출력 토큰 비율이 시간 비율은 아니다.
- **병목에는 조건이 있다.** 충분한 입력을 처리하는 prefill은 연산량, 작은 배치의 decode는 메모리 이동에 제약받기 쉽다. 배치·문맥·모델 구조가 바뀌면 병목도 달라진다.
- **지연과 처리량을 함께 잰다.** 요청 하나의 완료 시간과 초당 완료 요청 수는 다른 지표다.
- **알고리즘 보장과 수치 재현성을 구분한다.** 무손실 샘플링도 부동소수점·배치 조건에 따른 출력 차이까지 없애지는 않는다.

## 세부 설명

### 요청 하나가 지나는 두 단계

입력 → prefill → KV 캐시 → 반복 decode → 출력 순서로 진행된다.

**prefill**은 이미 주어진 입력 토큰들을 병렬 계산하여 첫 출력 토큰 생성에 필요한 상태를 만든다. **decode**는 앞서 생성한 토큰을 사용하여 다음 토큰을 순차 생성한다. 작은 배치에서는 연산기를 충분히 활용하지 못하고 가중치·KV 캐시 등의 메모리 이동 비용이 지연을 지배하기 쉽다. 배치가 커지면 여러 요청이 가중치 읽기 비용을 공유한다.

가중치 읽기만 병목인 dense 모델의 단순 근사에서는 `읽는 바이트 / 유효 메모리 대역폭`으로 한 단계의 비용을 추정할 수 있다. 하지만 이 근사는 KV 읽기, 연산, 통신, 커널 실행 비용을 생략한다. MoE의 활성 전문가와 배치 내 공유까지 고려하지 않은 전체 파일 크기를 보편적인 토큰당 시간 하한으로 쓰면 안 된다.

### 내 워크로드는 어느 쪽인가

| 워크로드 | 먼저 확인할 항목 |
|---|---|
| 긴 입력·짧은 출력 | prefill 시간, 공통 prefix의 캐시 적중, 대기 시간 |
| 짧은 입력·긴 출력 | decode 시간, 토큰 사이 지연, 배치 크기 |
| 높은 동시성 | 처리량, 대기열, preemption, 지연 분포 |

4000토큰 입력에 30토큰 출력이라도 decode가 전체 시간의 1%라고 결론 내릴 수 없다. 입력은 병렬로, 출력은 순차로 처리하기 때문이다. 서버의 단계별 시간 지표로 판단한다. TTFT(첫 토큰까지의 시간)에는 대기와 입력 처리 등이 포함되므로 prefill 시간과도 구분한다. 지표 해석은 `concepts/vllm-serving-operations.md`를 참고한다.

### KV 캐시 — 앞 문장을 다시 계산하지 않기 위한 저장소

attention에서 재사용할 key·value 상태를 보관한다. 요청 길이와 동시 요청 수가 늘면 캐시 사용량도 늘어난다. 캐시 용량을 요청당 최대 길이로 나눈 값은 모든 요청이 최대 길이를 쓴다는 가정의 동시성 추정치다. 실제 동시성은 요청 길이, 스케줄러 상한, 캐시 공유, 모델 구조에도 의존한다.

### 처리량과 지연

- **지연(latency)**은 요청 하나의 시작부터 완료까지 걸린 시간이다.
- **처리량(throughput)**은 단위 시간당 완료 요청 수 또는 처리 토큰 수다.
- **배치(batching)**는 요청들을 함께 계산하는 것이고, **동시성(concurrency)**은 동시에 진행 중인 요청 수다.

배치를 키우면 자원 활용이 좋아질 수 있지만 대기나 한 단계의 계산 시간이 늘 수 있다. 총 벽시계 시간을 완료 건수로 나눈 값은 처리량의 역수이며, 동시 실행에서 개별 요청 지연의 평균과 같지 않다.

### 모델을 작게 만드는 법 — 양자화

양자화는 가중치나 활성값을 적은 비트로 표현하여 메모리·연산 비용을 줄이는 방법이다. `W4A16`은 가중치 4비트·활성값 16비트라는 뜻이다. 속도 이득은 지원 커널, 역양자화 비용, 배치, 실제 병목에 따라 달라져 용량이 절반이라고 속도가 두 배가 되지는 않는다. 품질도 별도로 평가한다.

`AWQ`·`GPTQ`는 양자화 방법이며, `group_size`는 스케일을 공유하는 가중치 묶음의 크기다. 일부 레이어를 양자화에서 제외하면 명목 비트 수보다 실제 메모리가 커진다. 배포판의 양자화 설정과 실제 적재 메모리를 함께 확인한다.

### 모델을 덜 쓰는 법 — MoE

**MoE(Mixture of Experts)**는 토큰마다 일부 전문가를 선택한다. 총 파라미터 수와 활성 파라미터 수가 다르므로 연산량을 줄일 수 있지만, 가중치 저장과 전문가 간 통신·부하 불균형 비용은 남는다. offloading이 없는 일반적인 배치에서는 전체 전문가 가중치를 장치들에 적재한다. 활성 파라미터가 같다고 작은 dense 모델과 속도가 같다고 보장할 수는 없다.

### attention과 캐시의 관계

| 방식 | 기본 특성 |
|---|---|
| full attention | prefill의 attention 계산은 시퀀스 길이에 대해 제곱으로 증가한다. KV를 재사용하는 decode 한 단계와 구분한다. |
| sliding window | 최근 일정 구간을 참조하여 비용을 줄인다. |
| linear attention | 과거를 상태로 요약하는 방식이며 full attention의 KV와 관리 방식이 다르다. |
| hybrid attention | 서로 다른 방식을 레이어별로 조합한다. |

캐시 공유와 메모리 할당은 엔진·모델 지원에 따라 달라진다. linear/hybrid라는 이름만으로 prefix caching의 지원 여부나 기본값을 판단하지 않는다.

### 계산을 건너뛰는 법 — prefix caching

동일한 prefix의 계산 결과를 재사용한다. vLLM은 앞선 prefix와 현재 블록의 토큰 등을 해시에 반영하고, 완전한 블록을 캐시한다. 뒤쪽 문자열만 같아서는 공유되지 않는다.

재사용된 토큰 수의 비율은 실행 시간 절감률과 같지 않다. 남은 입력 처리, 캐시 조회, 스케줄링, decode 비용이 있기 때문이다. 모델 비교에서는 캐시 활성화 여부와 cold/warm 조건을 맞춘다.

### 미리 추측하는 법 — speculative decoding과 MTP

초안 토큰들을 먼저 제안하고 target 모델이 검증하여 여러 토큰을 한 번에 진행하는 방법이다. 올바른 rejection sampling은 target 분포를 보존한다. 이는 실행마다 같은 문자열을 낸다는 보장과 다르다. vLLM은 greedy 동일성을 검증하지만 부동소수점과 배치 크기에 따른 출력 변동 가능성도 명시한다. 차이가 나면 수치 조건과 구현을 함께 조사한다.

**MTP(Multi-Token Prediction)**는 모델 계열이 제공하는 다중 토큰 예측 기능을 사용하는 방식이다. 지원 모델이 필요하며, 계열에 따라 assistant 체크포인트를 지정할 수도 있다. **draft**는 제안한 토큰이고 **채택률(acceptance rate)**은 검증을 통과한 비율이다. vLLM 문서가 제시하는 추측 깊이 1은 시작값이며 보편적인 최적값이나 채택률 90%를 보장하지 않는다.

추측·검증의 추가 연산과 메모리 비용을 감안하여 측정한다. 중저부하의 메모리 병목 decode는 유력한 적용 대상이지만, 고부하에서도 이득을 얻는 방법이 있다. vLLM의 방법 선택 표는 정성적 안내이며 성능 보장이 아니다. prefix caching과 함께 사용한 전체 지연·처리량도 비교한다.

### 서버를 띄울 때 만나는 설정값들

메모리 사용률은 엔진 예산, 최대 문맥 길이는 요청 길이 상한, 최대 동시 요청 수는 스케줄링 상한이다. CUDA graph는 반복 실행 오버헤드를 줄이는 대신 준비 시간과 메모리를 사용한다. 기동 실패는 실패 단계와 오류를 확인하여 예산·캡처·모델 지원 문제를 좁힌다.

chunked prefill은 긴 입력을 나누어 decode와 함께 배치하는 방식이다. 구체적인 스케줄링과 설정 상충은 `concepts/vllm-serving-operations.md`에서 다룬다.
