# 김상국 (2026) — AI가 내 프롬프트를 흘려듣는 이유: 원리부터 다시 본 컨텍스트 엔지니어링

- **저자**: 김상국
- **연도**: 2026
- **매체/학회**: 우아한형제들 기술블로그 (techblog.woowahan.com)
- **링크**: https://techblog.woowahan.com/26459/
- **유형**: 2차 자료

## 핵심 요지

프롬프트에 규칙을 아무리 자세히 적어도 모델이 "흘려듣는" 원인은 팁 부족이
아니라 **LLM이 글을 읽는 원리**에 있다. 어텐션은 순서가 아니라 관련도로 읽어
무관 정보가 능동적 노이즈가 되고(입력이 길수록 주의가 묽어짐), 입력 중간의
정보는 덜 참조되며(lost-in-the-middle), 유한한 컨텍스트 윈도우를 시스템
프롬프트·대화 이력·도구 결과·생성 답이 나눠 쓴다. 따라서 한 줄을 영리하게
쓰는 **프롬프트 엔지니어링**에서, 모델이 볼 전체 토큰을 *무엇으로·얼마나·어떤
순서로* 채울지 설계하는 **컨텍스트 엔지니어링**으로 옮겨야 한다. 지식은
가이드라인, 행동은 하네스로 분담한다.

## 주요 내용

### 왜 가이드에 다 적었는데 안 되나

규칙을 빠짐없이 적어도 실행마다 다르게 해석·위반한다. 저자는 팁을 더
수집하는 대신 "LLM이 글을 어떻게 읽는가"라는 원리로 돌아간다.

### 첫 번째 질문 — LLM은 글을 어떻게 읽는가 (세 가지 기제)

- **어텐션은 관련도로 읽는다**: 모든 단어 쌍의 관련도를 계산하므로 입력이
  길수록 계산량이 제곱으로 늘고 주의가 묽어진다. 관련 없는 정보는 단순
  노이즈가 아니라 **적극적으로 해롭다** — 관련된 지시와 자료가 함께 묶여야
  어텐션 가중치가 높다.
- **lost-in-the-middle**: 정보가 입력 중간에 있으면 활용도가 떨어진다. 핵심
  지시는 앞이나 끝에 두고, XML 태그·markdown 제목으로 위치 표지를 준다.
- **컨텍스트 윈도우는 유한한 작업 공간**: 시스템 프롬프트·대화 이력·도구
  결과·생성 중인 답이 같은 공간을 나눠 쓴다. 누적된 대화·중간 결과가 중요한
  가이드를 "책상 밖으로 밀어낸다".

### 두 번째 질문 — 그래서 지금은 어떻게 쓰나

- **설계 3원칙**: (1) 관련된 것만 넣는다(큐레이션) (2) 핵심 지시는 앞·끝에
  (3) 최소 길이 — 길이는 비용이자 노이즈다.
- **가이드라인 vs 하네스 분담**: *가이드라인*은 모델이 **무엇을 알아야
  하는가**(지식·맥락: 규칙·정의·예시) — 모델이 도메인을 모를 때 강하다.
  *하네스(프롬프트)*는 모델이 **어떻게 행동해야 하는가**(절차·검증·중단 조건:
  출력 형식 계약·검증 루프) — 입력이 들쭉날쭉해도 일관성이 필요할 때 강하다.
- **모호한 규칙 → 원자 단위 분해**: 장문 규칙을 원자 단위 체크리스트로 쪼개고,
  각 결정을 특정 레이어에 고정해 **결정의 소유권을 레이어별로 고정**한다.
- **모델 세대별 조정**: 최신 추론 모델은 절차를 최소화하고 "무엇이 성공인지"만
  제시 — few-shot은 형식·톤 고정용, "단계별 사고" 강제는 오히려 성능을
  떨어뜨린다. 구형·경량 모델은 few-shot·단계별 가이드가 여전히 유효하고 검증
  규칙을 더 촘촘히 준다. *원리는 불변이나 권장 사용법은 모델 세대에 따라
  바뀐다.*
- **아첨(sycophancy) 대응**: RLHF 모델은 사용자에게 동의하려는 경향이 있다.
  "이거 괜찮지?"(확인)를 "약점과 반례부터 찾아줘"(반증)로 재구성한다.
- **하위 에이전트 오케스트레이션**: 상위 에이전트의 누적된 맥락은 노이즈다.
  정제된 목표만 들려 하위 에이전트를 깨끗한 새 컨텍스트에서 돌리는 편이 그
  작업엔 더 정확하다.

### 사례 — 사내 디자인시스템 MCP 프롬프트 개선

- **컴포넌트 선택 사다리**: "완성형 → 빌딩블록 → 토큰 기반 custom → raw" 순으로
  **한 단계씩만** 내려가게 강제.
- **사후 검증 규칙셋 16개**: 생성이 끝난 코드를 컴포넌트 manifest·토큰·아이콘
  카탈로그의 확인 사항을 기준으로 점검.
- **결과**: 규칙 위반이 "5번에 1~2번 → 10번에 1번 미만"으로 감소, 실행마다의
  일관성 개선.

### 정리 — Do / Don't

| Don't (예전 습관) | Do (지금) |
|---|---|
| 관련 있어 보이면 일단 다 넣는다 | 필요한 것만 골라 넣는다(큐레이션) |
| 중요도와 무관하게 지시를 늘어놓는다 | 핵심 지시는 앞이나 끝에 둔다 |
| 길수록 정확하다고 믿는다 | 길이는 비용·노이즈, 충분한 만큼만 |
| 절차를 하나하나 떠먹인다 | 목표·성공 기준을 주고 맡긴다 |
| 금지 사항을 잔뜩 나열한다 | 원하는 행동을 긍정형으로 지시한다 |
| 로직까지 few-shot으로 가르친다 | 예시는 형식·톤 고정용으로만 |
| 규칙을 특정 케이스로 못 박는다 | 경계를 원리로 적는다 |
| 큰 작업을 프롬프트 하나에 몰아넣는다 | 하위 작업은 정제된 목표만 줘 분리한다 |
| "이거 괜찮지?"로 확인받는다 | "약점과 반례부터 찾아줘"로 검증시킨다 |
| 한 번 잘 나왔으니 늘 그렇다고 믿는다 | 출력은 확률이라 흔들린다, 중요한 건 재확인 |
| 최신 모델이니 무조건 짧게 쓴다 | 대상 모델 성격에 맞춰 조절한다 |

저자의 결론: "진짜 실력은 검증과 판단 그리고 방향 설정에 있다." 핵심은
"모델에게 잘 부탁하는 법"이 아니라 "모델이 어떻게 읽는지 알고 무엇을
컨텍스트로 제공할지 설계하는 일"이다.
